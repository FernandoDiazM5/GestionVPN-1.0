## 4) 🔒 Reglas e invariantes del proyecto (NO romper)

Estas reglas son **durables**: aplican a toda sesión y a todo cambio. Si una feature necesita salirse de aquí, documentarlo explícitamente antes.

1. **Alta de nodo = todo server-side.** Dar de alta un nodo debe ser como dar de alta un usuario: el servidor **genera TODO** (llaves WG, usuario/contraseña SSTP, rutas de retorno) y entrega **un único script para pegar en el CPE**. El modo experto (pegar llaves/usuario propios) va OCULTO tras "Opciones avanzadas". Nunca volver a pedir la clave pública del CPE en el flujo normal.
2. **Toda la infra por-túnel se crea sola** (mangle, rutas de retorno, scan-route, IP de gestión por nodo). Nada de `.rsc` manual en el flujo normal.
3. **Aislamiento multi-usuario — mangle POR-USUARIO (sin colisión).** Cada moderador marca **solo su propio tráfico**: `comment=ACCESO-USER-<tag>`, `src-address=<su mgmt_ip>` → `new-routing-mark=<su VRF>`. **PROHIBIDO** crear reglas mangle GLOBALES (`ACCESO-ADMIN`/`src=<toda la /24>`): rompen el aislamiento y el backend las elimina. `mgmt_ip` + VRF se resuelven **server-side** desde la sesión activa (`sessionRepo.getActiveByUser`), **nunca** desde un IP del body. Usar `tunnelProvisioner.addUserMangle`. Aplica a activate, keepalive **y reparación**.
4. **Varios nodos pueden compartir la misma LAN a propósito** (arquitectura VRF + mangle). NO añadir avisos de "solape de LAN" como si fuera un error (memoria `arquitectura-lan-compartida-vrf-mangle`).
5. **Antispoofing en escaneo/Monitor AP:** la IP y credenciales del equipo se resuelven **server-side** del nodo/AP dueño (`ipInOwnedSubnet`, `ownsApUuid`), nunca del body del cliente. El navegador no envía contraseñas SSH.
6. **🛑 Operaciones SSH sobre antenas Ubiquiti airOS — SOLO:** lectura de estado + diagnóstico activo (ping/traceroute) + reinicio con confirmación explícita. **NUNCA:** actualizar firmware, borrar archivos, restaurar a fábrica, modificar config persistente, apagar, gestionar usuarios SSH, ni **polling SSH automático** (§43 del LOG). Detalle completo y matriz de comandos: sección "Política SSH" en [`HANDOFF_LOG.md`](./HANDOFF_LOG.md).
7. **Sistema de diseño:** color = intención, movimiento = estado (no decorativo). Usar clases del sistema (`.btn-*`, `.badge-*`, `.card`, `.modal-overlay/.modal-panel`, `.skeleton`, `.status-live`). Dark mode por clase; toda animación respeta `prefers-reduced-motion`. `text-xs` mínimo. Gate CI `audit:design` debe quedar en **0 errores**. Menús de acción **con color** (no gris) — memoria `pref-menu-accion-con-color`.
8. **No versionar secretos:** `.jwt_secret`, `.db_secret`, `database.sqlite*`, `.claude/worktrees/`, binarios. (El historial ya se purgó 2×; en el VPS usar `git fetch && git reset --hard origin/main`, NUNCA `git pull`.)
9. **`/settings/save` y config del router core = solo `platform_admin`.** Un moderador no muta settings globales por API.
10. **`.conf` de gestión = SPLIT-TUNNEL, NUNCA `0.0.0.0/0` (ni `0.0.0.0/1, 128.0.0.0/1`, que es lo mismo).** El router no da salida a internet a los clientes de gestión (CLIENTES); solo el plano ADMIN tiene internet (`Admin MGMT libre`+NAT). `0.0.0.0/0` deja a CLIENTES **sin internet**. AllowedIPs = base RFC1918 (`mgmtNet.mgmtAllowedIps`, env `MGMT_ALLOWED_IPS`) **+ LAN públicas de torre leídas DINÁMICAMENTE** del address-list `LIST-NET-REMOTE-TOWERS` del router (`readTowerLans` + `mgmtAllowedIpsFor(ws, {addressList})` en `lib/mgmtAllowedIps.js`) → cubre `142.152.7.0/24`, `142.153.0.0/24`, etc. sin hardcodear. Las privadas ya las cubre la base.
11. **Clasificar caídas del túnel como inalcanzable (503), no 500.** `isUnreachable` debe incluir cortes transitorios (`ECONNRESET`/`EPIPE`/`EHOSTDOWN`/`socket hang up`) para que la UI muestre el overlay "Router no alcanzable · Reintentar" en vez de un 500 duro.
12. **Borrar un moderador = de-provisionar sus nodos del router.** El cascade (`DELETE /admin/moderators/:id`) debe llamar `deprovisionNodeOnRouter` (`lib/nodeDeprovision.js`) por cada nodo (VRF + interfaz + rutas + mangle + peer), además de borrar peers de gestión (`routerCleanup`/`routerPeerState`, que usan `mgmtNet.userIfaces`, NO `VPN-WG-MGMT`). Best-effort: el router caído no bloquea el borrado en BD.
13. **NUNCA tocar el address-list `LIST-NET-REMOTE-TOWERS` al de-provisionar.** Varias torres comparten la misma LAN (aislamiento por VRF+mangle) → borrar la entrada rompería a los nodos hermanos. Las entradas sin ruta/VRF quedan inertes.
14. **IPs de gestión: amarradas al usuario, liberadas y reutilizadas.** `user_mgmt_ips` (`uq_umi_user`+`uq_umi_ip`) amarra 1 IP↔1 usuario; al borrar se libera. La asignación usa **menor octeto libre** (`lib/ipAlloc.lowestFreeOctet`), no `max+1` → reutiliza huecos de usuarios borrados.
15. **Scan-IP del VPS = amarrada al WORKSPACE, asignada al crearse — y AUTO-ASIGNADA al activar túnel si falta.** `workspace_scan_ip` (`uq_wsi_workspace`+`uq_wsi_ip`) liga 1 scan-IP↔1 workspace. Se asigna **automáticamente** al crear el workspace (`scanIpRepo.allocateInTx` dentro de `workspaceRepo.createForOwner`, menor IP libre del pool `10.11.252.0/24`), best-effort: pool agotado NO rompe la creación. **Red de seguridad (cont. 18, `aa1864a`):** si un workspace llega a activar túnel SIN scan-IP (creado pre-Opción C, o la asignación al crearse falló), `scanMangleSync.onTunnelActivated` la asigna del pool **al vuelo** en modo `vps` (`scanIpRepo.allocate`, idempotente) antes de montar la mangle — sin esto la mangle `SCAN-WS` no se montaba y el escaneo daba 0 en silencio (caso TorreOMAR/FIWIS). En modo `local` no aplica (IP global). `scan:assign` queda solo como herramienta manual de emergencia. NUNCA tomar la IP del request del cliente — siempre server-side (`resolveForWorkspace`). Se eligió el **workspace** (no el usuario) porque es el contenedor estable: sobrevive a rotación del moderador y el namespace de mangle ya es `SCAN-WS-<ws>`.
16. **Un solo moderador (OWNER) por workspace — sin co-moderadores.** El rol `CO_MODERATOR` está **retirado** del enum, contratos, guards, rutas y UI. `isModerator` = `OWNER` (o `platform_admin`). No hay promover/degradar (endpoint `/team/role` eliminado); `/team/invite` solo crea MEMBERs. El alta de un moderador la hace el Administrador (invitación rol `OWNER`). Job de Monitor AP: `scanLock.tryAcquire` (no bloqueante) para no estancar otros workspaces durante un escaneo interactivo largo.

Toda operación de router es best-effort: una caída/cuelgue del router **nunca** debe bloquear una petición HTTP (el frontend no tiene timeout de fetch). Patrón: hacer el trabajo de BD y responder primero; la limpieza/sync del router corre aparte.
18. **El plano de gestión `10.x` debe estar en `/ip service api address=` (y `api-ssl`), no solo en el firewall.** `/ip service api` tiene su PROPIA allow-list por `address=`, **independiente** del firewall y de `LIST-MGMT-TRUSTED`. Si el origen del backend (`10.13.250.x`/`10.14.250.x`) no está ahí, RouterOS acepta el TCP pero **descarta el login en silencio** (no `!trap`, no cierre: cuelgue). El **retorno del scan SSTP lo resuelve el `masquerade out-interface-list=LIST-VPN-SSTP`** del Core (reescribe el origen a la PPP-local `10.11.251.1` → el CPE no necesita ruta del scan-pool; conntrack des-NATea). La mangle `SCAN-WS-<ws>` marca `src=scan-IP AND dst-address-list=LIST-NET-REMOTE-TOWERS` → por eso la LAN DEBE estar en esa address-list (la añade `addTowerEntries` al provisionar).

29. **La mangle de ESCANEO (`SCAN-WS-<ws>`) vive y muere con el TÚNEL del moderador, NO con un timer; y el scan-lock debe ser anti-fuga.** (a) **Ciclo de vida:** la mangle `src=scan-IP → VRF` se crea/re-apunta al **activar** el túnel y se borra al **desactivar/expirar** (`lib/scanMangleSync.onTunnelActivated/onTunnelClosed`, disparadas por `tunnelService` y `expirationJob`; best-effort, `tryAcquire`, no-op sin scan-IP). El escaneo interactivo sigue haciendo `setup` idempotente como red de seguridad. Válido porque el sistema fuerza **1 sesión ACTIVE por usuario** (`sessionRepo.createSession`) + **1 moderador/ws** → la scan-IP solo apunta a 1 VRF a la vez. Entre workspaces son independientes (cada uno su scan-IP del pool `10.11.252.0/24`) → escaneo en paralelo intacto. (b) **Lock anti-fuga:** `scan.routes` DEBE registrar el cierre del cliente (`req.on('close')`/flag `clientGone`) **ANTES** de `await scanLock.acquire*`, o una petición que muere esperando el lock (nginx corta a ~60s → 504) lo deja tomado 5–7 min y los reintentos se apilan (síntoma: "hay que reiniciar el backend"). Usar `scanLock.acquireOrNull(key, waitMs, maxMs)` (espera ACOTADA, cancelable sin filtrar la cola) → responder **409 `SCAN_BUSY`** si el lock está ocupado, nunca bloquear hasta el 504. NO tocar el job de Monitor AP (`apPollJob` se auto-gestiona bajo el mismo lock con `tryAcquire`).

30. **La mangle de escaneo (`SCAN-WS`) es propiedad EXCLUSIVA del túnel; Monitor AP exige túnel activo; las credenciales SSH viven en el backend.** (a) **Ciclo de vida de la mangle:** la crea **SOLO** `scanMangleSync.onTunnelActivated` (al activar el túnel del nodo) y la destruye **SOLO** `onTunnelClosed` (deactivate/expiración). **NINGÚN otro sitio la toca** — ni `scan-stream`, ni `poll-direct`, ni `apPollJob` (que ANTES la montaba/desmontaba cada tick de 60s → la "tumbaba sola luego de un minuto"). Como hay 1 túnel activo por usuario, hay 1 mangle de escaneo a la vez, amarradas. `scanMangleSync` NO usa lock (es el único gestor → sin contención). (b) **Monitor AP solo LEE, atando el SSH a la scan-IP** (la mangle ya está viva si el túnel está activo). Toda operación SSH de Monitor AP (`poll-direct`, `cpe/ap-detail-direct`, `enrich-batch`, `apPollJob`) pasa por `resolveTunnelBinding(req, vrf)`: sin scan-IP (dev local) → SSH directo; con scan-IP (VPS) y **túnel del nodo NO activo** (no hay sesión viva de ese VRF) → **409 `TUNNEL_NOT_ACTIVE`** (el `apPollJob`, de fondo, simplemente salta el AP). El frontend muestra `TunnelInactiveModal` ("Activá el túnel" → `setActiveModule('nodes')`). NUNCA montar la mangle desde Monitor AP. (c) **La clave SSH que autentica una antena en el escaneo DEBE llegar al backend (`aps.clave_ssh_enc`)**, no solo a `credCache` (IndexedDB del navegador): Monitor AP/`apPollJob` corren server-side y leen `aps`. `deviceDb.saveSingle` rellena `sshPass` desde `credCache` si falta antes del POST; `deviceDb.load` re-empuja (PUT parcial) las claves que el backend reporta ausentes pero `credCache` tiene. Revelar la clave: `POST /api/ap-monitor/reveal-ssh` (descifra server-side, `ownsApUuid`).

31. **Todo runner de `.sql` DEBE partir por `split(/\r?\n/)`, NUNCA `split('\n')`, antes de quitar comentarios.** Los `.sql` del repo se leen, se les quitan los comentarios `--` con `/--.*$/` y se parten por `;`. Con checkout **CRLF** (Windows) el `\r` queda al final de cada línea y `.` del regex NO lo cruza → el comentario **sobrevive**, y un `;` dentro de un comentario inline parte el `CREATE TABLE` a la mitad (`ER_PARSE_ERROR near ''`). Afecta a BD fresca en Windows. `db.service.js` (`b964309`) ya lo tenía; `initRbac.js`/`initMultiuser.js` (`df0fde6`) se alinearon. Cualquier runner/migración nueva que parsee SQL sigue el mismo patrón. **Corolario:** los índices de perf viven en `schema_perf_indexes.sql` (aplicados por `migrate:perf`, idempotente por `information_schema`); si añades un índice al hot path, ponlo ahí **y** en el `CREATE TABLE` del schema base (para BD fresca).

32. **Un `403` NO es siempre sesión expirada — el frontend solo desloguea si el backend lo marca `logout:true`.** `apiClient.apiFetch` intercepta 401/403 fuera de `/api/auth/`: **401** = sesión muerta siempre (desloguea); **403** = AMBIGUO (puede ser permisos, ej. `requireOperator` a un MEMBER, o token expirado). Tratar TODO 403 como expiración deslogueaba al MEMBER **en cadena** al activar un túnel compartido (el `/node/history/add` con `requireOperator` devolvía 403 de permisos → `auth_expired` → logout → re-login → repite). El token expirado REAL sí trae `logout:true` (`auth.middleware.js` línea del Bearer). Corolario backend: los endpoints append-only de bitácora (`/node/history/add`) se gatean por **workspace** (`nodeBelongsToRequester`), NO por rol — un MEMBER registra eventos de sus nodos asignados. Solo las MUTACIONES de nodo llevan `requireOperator`.
33. **El autosync del `wg0` DEBE crear la ruta de kernel, no solo el AllowedIPs.** `wg syncconf` actualiza los AllowedIPs internos de WireGuard pero **NO crea la ruta `ip route … dev wg0`** (eso lo hace `wg-quick up`). Sin la ruta, el tráfico a la LAN de la torre sale por la default (`eth0`) y se pierde → escaneo 0 (síntoma: la LAN está en `AllowedIPs` pero `ip route get <LAN>` da `dev eth0`). `wg0-autosync.sh` reconcilia rutas con `ip route replace <cidr> dev wg0` (idempotente) en CADA corrida, aunque el AllowedIPs no cambie. Diagnóstico: `ip route get <ip-LAN>` debe dar `dev wg0`.
34. **El autosync del `wg0` se reconcilia también al ARRANCAR el backend (no solo event-driven).** El hook `autosyncWg0` (provisión) registra la LAN de una torre en el archivo de intención SOLO en ese instante; si esa escritura falla (permisos del dir) o el nodo se creó antes del hook, la LAN se perdía para siempre. `lib/wg0Reconcile.reconcileOnStartup()` (en `index.js` tras los jobs) re-siembra la intención con TODAS las LAN de `nodes` en cada arranque (idempotente, best-effort, no-op fuera del VPS) → recupera cualquier LAN perdida sin entrar al VPS. **El dir de intención `/opt/wg0-autosync` (bind-mount `/wg0sync`) DEBE ser escribible por el uid del backend (1001)** — si no, la escritura falla y hoy queda `log.error` VISIBLE (antes: silencio); se cura con `chown -R 1001:1001 /opt/wg0-autosync`. **NO meter `10.0.0.0/8` ni `172.16.0.0/12` en el AllowedIPs del wg0:** el VPS usa `10.48/16`+`10.124/20` (VPC DigitalOcean) y `172.17/172.18` (Docker) → el superset los secuestraría. Solo `192.168.0.0/16` es seguro como base, pero con el autosync arreglado ya no hace falta (cada LAN entra sola).
35. **MariaDB 11.4+ crea tablas nuevas en `utf8mb4_uca1400_ai_ci` → todo JOIN entre columnas de tablas con collation distinta revienta "Illegal mix of collations".** `migrateScanIp` fuerza `workspace_scan_ip` a `general_ci`, pero `workspaces` (creada fresca en prod) queda en `uca1400` → el JOIN `w.id = wsi.workspace_id` explota. Fix: `COLLATE utf8mb4_general_ci` EXPLÍCITO en AMBOS operandos del JOIN (robusto ante cualquier combinación). El hot path del escaneo NO se afecta (`getScanIpForWorkspace` usa `WHERE = ?` con parámetro, sin JOIN entre columnas). Si añades un JOIN nuevo que cruce `workspace_scan_ip` con otra tabla, aplica el mismo `COLLATE` en ambos lados.

36. **El bootstrap del Router Core (Servidor VPN) es IDEMPOTENTE, derivado de `mgmtNet`, y con ANTI-BLOQUEO.** `lib/coreBootstrap.js` reconstruye la config base del Core por la RouterOS API — el `.rsc` (`vpn_habil.rsc`) es la ESPECIFICACIÓN, NO se pega. **Nunca hardcodear `10.1x.250.`/`VPN-WG-*`**: todo sale de `mgmtNet`. Cada objeto se **lee-antes-de-crear** (como `addRouteOnce`) → re-ejecutar = todos `skip` (no duplica; RouterOS PERMITE duplicados en reglas/rutas). **Anti-bloqueo (§4.18):** la regla `drop chain=input in-interface-list=LIST-WAN` y la restricción de `/ip service api,api-ssl address=` SOLO se aplican si el origen del backend está garantizado en `LIST-MGMT-TRUSTED` (detectado con `detectBackendOrigin` vía `/ip firewall connection`, o conectando por el plano `10.x`); si no (bootstrap sobre IP pública sin poder resolver el origen) se **OMITEN con `warn`** — nunca se deja sin acceso a un router recién levantado. La allowlist de la API se toca **solo por UNIÓN** (nunca quita el origen vivo). Persistir `MT_*` **solo tras éxito**. Clasificación de estado: `blank`/`ours`/`partial`/`foreign` (para "validar si ya existe / cambiar de equipo"; `409 CORE_DEVICE_CHANGE` con confirmación). Solo `platform_admin`.
37. **El bootstrap del Core NO gestiona la IP pública / WAN.** La IP pública la provee la nube (CHR de DigitalOcean con su pública ya asignada) o la habilita el operador con SUS propias configuraciones (dirección WAN, `src-nat` de la pública, miembro de `LIST-WAN`). El bootstrap monta **solo el andamiaje VPN** ("el resto"): NO detecta la interfaz WAN, NO crea la regla `src-nat "NAT IP Publica"`, NO añade ningún miembro a `LIST-WAN` (solo crea la lista, inerte hasta que el operador le añada su WAN). La IP que ingresa el admin se usa para **conectar** (`MT_IP`) y como default del endpoint CPE (`server_public_ip`, **solo si está vacío** — nunca pisa lo que el operador ya configuró). **Redes de gestión extra:** el wizard acepta `trustedNets` (CIDR, "Opciones avanzadas") — la LAN local del admin (ej. `192.168.18.0/24` por Winbox) además del túnel `10.x`; el bootstrap las mete en `LIST-MGMT-TRUSTED` + allowlist api/api-ssl (por UNIÓN) para que el blindado NO deje sin acceso a esa red. Sin ellas, un equipo blindado solo se administra por el plano `10.x`.

38. **Tras cualquier reset / restore / backup-viejo del Core, RE-VERIFICAR `/ip service ... address=` — un restore puede revertir la restricción de la §4.18 y re-exponer API/Winbox/SSH a internet.** Los servicios de gestión (`api`, `api-ssl`, `winbox`, `ssh`) deben aceptar SOLO desde los planos de gestión `10.x` + la LAN admin local; `telnet/ftp/www` disabled. **Incidente 2026-07-08:** fuerza bruta al `api` desde `45.198.224.18` (diccionario admin/root/support/… vía API) porque el reset del Core del 2026-07-03 (cont. 16) borró la allowlist `/ip service api address=` → API abierto a internet. **Diagnóstico rápido:** si el Log del router muestra `login failure … via api` (o winbox/ssh) desde una IP PÚBLICA, el servicio está expuesto → cerrar `address=` YA (§4.18). El bootstrap del Core (§4.36) deja el equipo así de fábrica; esta regla cubre los equipos EXISTENTES/restaurados que el bootstrap no re-tocó.

39. **Cuenta LOCAL (usuario sin correo real) = email SINTÉTICO `<username>@local.app`; NUNCA columna nullable ni migración.** `users.email` es NOT NULL + UNIQUE; un moderador creado solo con `username` recibe `syntheticEmail(username)` (fuente única en `@gestionvpn/contracts`, reexportado por `lib/localAccount.js`). El UNIQUE del email da gratis la unicidad del username. El login corto ya resuelve (`sessionBridge`: sin `@` → añade `@local.app`, fallback `findByName`). Todo lo que envíe correo DEBE tratar el sintético como "sin email": `notifier.dispatchEmail` y `auth password-reset` lo saltan (`isSyntheticEmail`). `name` = username por defecto (mantiene vivo el login corto por `findByName` aunque luego asocie un correo real). El correo se asocia después en Perfil → Correo (mismo flujo OTP `PATCH /account/email/*`, que rechaza el dominio sintético como destino). `username` = 3–32, `[a-z0-9._-]` sin `@` (`UsernameSchema`); `admin`/`root`/`system` reservados. **RIESGO documentado:** renombrar el `name` de una cuenta local que ya asoció correo real rompe su login por username corto (queda el correo).

40. **Alta de moderador = email real XOR username (nunca ambos).** `CreateModeratorRequestSchema` con `.refine(email !== username)`. `POST /admin/moderators` rama username → 400 `USERNAME_RESERVED` / 409 `USERNAME_TAKEN` (colisión con el sintético) / 409 `NAME_CONFLICT` (colisión con el `name` de otro user, que rompería el login por nombre). Rama email real rechaza `@local.app` (`EMAIL_RESERVED_DOMAIN`). El flujo por invitación con correo queda intacto como 2º modo.

41. **Multi-workspace: la sesión lleva UN workspace activo en el JWT; el switch lo re-emite validando membresía SERVER-SIDE.** Un usuario puede ser OWNER de su workspace y MEMBER en otros (`workspace_members` ya es `UNIQUE(workspace_id,user_id)`, permite N filas). `findMembershipByUser` (login) toma la más antigua; `GET /account/workspaces` lista todas; `POST /account/switch-workspace` re-firma el JWT con `{workspace_id, role}` de la membresía destino (valida `memberRepo.findMembership` → 403 `NOT_A_MEMBER`) y **desactiva el túnel activo global del user** antes (la mangle del router es por-usuario → 1 túnel activo físico por persona). El token viejo NO da derechos sobre el destino. El frontend hace `window.location.reload()` tras el switch (VpnContext no se remonta con `refresh()`). Invitar a un user EXISTENTE por username → invitación in-app (`GET /my-invitations` + `POST /invitations/:id/accept`, que ya cambia el ws activo); si el email es sintético NO se envía correo.

42. **Multi-workspace — identidad de RED GLOBAL por persona + mangle scoped por workspace.** El peer WG y la mgmt-IP son ÚNICOS por persona (`migrate:globalwg` → `UNIQUE(user_id)` en `user_mgmt_ips`/`member_wireguard`; `workspace_id` queda informativo) y se reutilizan en todos sus workspaces. El `.conf` split-tunnel une las LAN públicas de TODOS sus workspaces (`mgmtAllowedIpsForUser`, NO `mgmtAllowedIpsFor` ws-scoped). Al **salir de un ws** el peer/IP se borran SOLO si no quedan otras membresías; al **borrar un moderador** las filas de los members que sobreviven se reasignan a su otro ws (la FK obliga). La **mangle por-usuario** (única física): `createSession` cierra la ACTIVE del user en TODOS los ws; `deactivateTunnel` NO toca la mangle si el túnel vivo del user es de OTRO ws; `removeUserMangles(userIds, {workspaceId})` salta a un user cuyo túnel activo es de otro ws (no le mata el acceso legítimo). La scan-IP y la mangle `SCAN-WS-<ws>` siguen atadas al WORKSPACE, nunca al user.

Ver también `vpn-manager/CLAUDE.md` y `DESIGN_SYSTEM.md`.

## 5) ⚙️ Procesos / funciones vigentes

> Aquí van los **flujos que siguen activos** (no cómo se construyeron). Cuando el usuario pida "enviar al handoff" una regla/función/proceso, va a §4 o §5.

- **Alta de nodo (WG):** backend genera el par de llaves si no se pega una propia, registra la pública en el peer del Core, embebe la privada en el script + rutas de retorno. Columnas `nodes.wg_cpe_public` + `wg_cpe_private_enc` (AES-GCM). Salida: script autocontenido.
- **Alta de nodo (SSTP):** no requiere ruta de retorno (RouterOS la arma con la `remote-address` del PPP). Usuario/contraseña PPP se generan server-side (`ppp-<nombre>-nd<ND>` + pass segura) y se embeben en el script.
- **Invitación de MEMBER (modelo seguro):** el invitado envía **solo su public key**; el server crea el peer, asigna el túnel de la invitación y devuelve `{allowedIp, serverPublicKey, endpoint, allowedIps}` para que arme su `.conf` (la clave privada nunca sale del dispositivo). Provisión WG = best-effort.
- **Recuperación WireGuard self-service:** `POST /api/team/me/wireguard` — el moderador/member (re)genera su propio acceso WG si quedó sin él (la provisión al aceptar es best-effort y puede fallar si el router está caído). UI en **Ajustes → tab WireGuard** (`WireGuardTab.tsx`) con QR + descargar `.conf` + regenerar. Idempotente: limpia el peer anterior al regenerar.
- **Vinculación de Telegram (3 pasos):** al tocar **Vincular** el server genera un código (`/link CODE`, 6 hex, TTL) y la UI muestra `TelegramLinkSteps`: **1)** instalar Telegram (link Play Store) → **2)** copiar el código → **3)** abrir el bot (`https://t.me/<username>`) y pegarlo. El `@username` lo autodetecta el backend (`lib/telegram.getBotUsername()` vía `getMe`, cacheado; override `TELEGRAM_BOT_USERNAME`) y viaja en `GET /account/notifications` como `telegramBotUsername`; si es null, la UI degrada (muestra el código sin enlace directo). El bot interactivo (long-polling) confirma con `/link CODE` (`telegramBot.js`). Local: SMTP por Gmail (`verify()` OK); **en el VPS DO bloquea 25/465/587** → email por puerto/relay alterno (lo gestiona el usuario), y el alta de moderador no depende del correo igualmente.
- **Enlace manual de invitaciones:** `invite-moderator` no falla si el email falla y devuelve `acceptUrl`; `GET /api/admin/invitations` lista pendientes y `POST .../:id/link` regenera el enlace. El admin lo comparte a mano cuando el correo no llega.
- **IP pública WAN:** setting global del admin (`server_public_ip` en Ajustes); `NuevoNodo` la consume en solo-lectura.
- **Escaneo Opción C (VPS):** una scan-IP por workspace (`workspace_scan_ip`), **asignada al crear el workspace**; mangle namespace `SCAN-WS-<ws>`; el SSH/HTTP se ata a la scan-IP (`localAddress`) y la mangle por-origen del router lo enruta al VRF. Serializado por `scanLock` (interactivo `acquireOrNull` con espera acotada → 409 `SCAN_BUSY` si ocupado; Monitor AP `tryAcquire`). La mangle `SCAN-WS` se crea/borra atada al ciclo del túnel (activate/deactivate/expiración, §4.29) — el escaneo solo hace `setup` idempotente de respaldo. Sin scan-IP → escaneo legacy (dev local). Ruta de retorno del scan-pool se crea sola al provisionar nodo (`provision.routes.addScanReturnRoute`); `db/checkScanRoute.js` la verifica/repara.
- **Modo de escaneo `local` (1 equipo) + alerta de IP obsoleta:** `app_settings.scan_mode='local'` hace que TODO el escaneo (interactivo, Monitor AP, auth SSH de antena — los 3 vía `scanIpRepo.resolveForWorkspace`) se ate a `local_scan_ip`, la IP WG de gestión de ESTE equipo. **Esa IP debe ser una interfaz viva del equipo** (la del cliente WireGuard, plano CLIENTES `10.13.250.x` para moderadores); si no, el `bind()` del probe falla en silencio → 0 resultados. Guardas: `lib/wgDetect.js` (detección read-only de IPs WG locales por plano, vía `mgmtNet`); el escaneo **corta con 409 `LOCAL_SCAN_IP_STALE`** (mensaje accionable) si la IP no está viva — **solo en modo local**; `GET /api/settings/scan-local-check` (platform_admin) + banner ámbar en `ScanModeToggle` avisan al admin con la IP WG detectada. El campo se configura en **Ajustes → Modo de escaneo** (`local_scan_ip`); NO se autodetecta/escribe (decisión: solo alertar, no auto-cambiar).
- **Autosync del `wg0` del VPS (event-driven, §4.27):** al provisionar una torre, su LAN debe estar en el `AllowedIPs` del `wg0` del VPS para escanearla. Modelo **HARDENED**: `provision.routes` (backend no-root) escribe la LAN en un archivo de **intención** (`/wg0sync/allowedips.desired`, bind-mount) vía `lib/wg0Sync.appendWg0Intent` — best-effort, `setImmediate`, no-op fuera del VPS. Un **watcher del host** (`systemd .path` → `wg0-autosync.sh` awk, root) añade la LAN al `wg0.conf` SOLO si falta y recarga con `wg syncconf` (sin cortar el túnel). **Guarda de idempotencia** en ambos lados (solo actúa si la LAN es nueva). El backend NO gana `NET_ADMIN`/root ni ve la clave privada. Reconciliación total/manual: `npm run sync:wg0` (CLI `db/syncWg0.js`, dry-run por defecto). Instalación host + verificación: [`deploy/wg0-autosync/README.md`](./deploy/wg0-autosync/README.md). Toggle: `WG0_AUTOSYNC=false`.
- **Auditoría "Actividad reciente" (módulo Equipo):** timeline de acceso a túneles del workspace. **Fuente de verdad = `tunnel_session_logs`** (escrita por `sessionRepo.log` en ACTIVATE/SWITCH/DEACTIVATE/EXPIRE/ERROR); `auditRepo.list`/`listForExport` leen de ahí (NO de la tabla legacy `tunnel_logs`, que nadie llena). **En vivo:** `tunnelService` y `expirationJob` emiten SSE `'tunnel'` → `useWorkspaceEvents` refresca el panel. **Retención rodante de 7 días:** `auditRepo.purgeOlderThan` lo dispara el `expirationJob` (throttle 1×/hora); env `AUDIT_RETENTION_DAYS` (default 7). **UI:** `AuditTimeline` pagina 8/página; export CSV/JSON por rango (`POST /api/audit/export`).
- **Habilitar router como Servidor VPN (bootstrap del Core, §4.36/§4.37):** en **Ajustes**, `CoreRouterWizard` guía al Administrador: ingresa **IP pública del router** (1er campo) + usuario + contraseña. `POST /settings/core-router/validate` conecta (sin guardar) y clasifica el equipo (`blank`/`ours`/`partial`/`foreign`) mostrando los valores vivos; `POST .../bootstrap` aplica el andamiaje base idempotente (`coreBootstrap.applyBaseline`, derivado de `mgmtNet`) y devuelve el **checklist** (✓/=/!) — solo tras éxito persiste `MT_*`/`server_public_ip`/`sstp_port`. `GET .../status` pinta el panel "conforme" con las creds guardadas. **Campo `trustedNets`** (Opciones avanzadas, cont. 20): redes de gestión extra de confianza (ej. la LAN local del admin `192.168.18.0/24`) que se añaden a `LIST-MGMT-TRUSTED` + allowlist api para que el blindado no lo deje sin acceso (§4.36/§4.38). Los **peers de gestión** (admin/members/VPS) siguen por los flujos existentes (invitación, recuperación WG self-service) — sembrarlos en el bootstrap = fase 2. Sin migración de BD.
- **Alta de moderador (2 modos, §4.39/§4.40):** el Administrador en **Moderadores → Nuevo Moderador** elige **Directo (usuario)** — `username`+contraseña (con botón Generar), sin correo → `POST /admin/moderators`, muestra las credenciales UNA vez — o **Por invitación (correo)** — flujo OTP por email existente. La cuenta local usa email sintético `@local.app`; el moderador asocia su correo real después en **Ajustes → Perfil → Correo** (la UI dice "Asociar correo" / "Sin correo asociado").
- **Multi-workspace: invitar a un usuario existente + cambiar de workspace (§4.41/§4.42):** el moderador en **Workspace → Invitar a un miembro** elige **Usuario existente** y escribe el username → invitación **in-app** (sin correo), que el invitado ve en su **bandeja** (`MyInvitationsInbox`, badge en el Sidebar) y acepta → queda MEMBER de ese workspace. El **`WorkspaceSwitcher`** del Sidebar lista sus membresías (`GET /account/workspaces`) y cambia el activo (`POST /account/switch-workspace` re-emite el JWT + `reload`); en cada workspace ve los túneles que le compartieron. Su acceso WG (peer/IP/`.conf`) es **global y único**, reutilizado en todos sus workspaces.

## 8) 🧭 Cómo mantener este documento

Este doc se mantiene con la skill **`handoff-keeper`** (`.claude/skills/handoff-keeper/SKILL.md`). En resumen:
- **Estado, reglas, funciones y procesos** → se **integran/actualizan en este `HANDOFF.md`** (§0, §4, §5) reemplazando lo viejo.
- **Narrativa de "qué hice esta sesión"** → se **añade** como nueva entrada arriba en [`HANDOFF_LOG.md`](./HANDOFF_LOG.md).
- Cuando el usuario diga *"envía esto al handoff"*: clasificar primero (¿regla/función/proceso durable, o evento de bitácora?) y colocarlo en el archivo correcto.
